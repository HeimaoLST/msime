# Agent Note: 后端汉字注音支持双拼按键反查

Status: implemented

## Problem

云端公共查询把双拼的汉字问题送进按键码候选接口，汉字不符合该接口的输入规则；模型因而报告四个方案都查询失败，无法核实完整按键码。现有注音能从发布词库获得读音，但不提供双拼编码。

## Decision

注音的默认全拼响应保持原样。显式 `scheme=shuangpin` 时，用同一次词库读音及现有双拼方案表生成完整按键码，同时返回全拼、两键分段和方案名称。编码属于 Rust Engine；Go 只校验、转发与归一化工具请求，不另存键位表。未知方案、非拼音方案或不可编码音节明确失败，不退回小鹤、不返回部分结果。

## History audit

检索 backend、annotate、双拼编码与反查相关活跃笔记。双拼编码判定、模糊候选重标和九键编码笔记分别约束解码、展示和触屏路径，部分相关但没有复用反查接口；client-core 拆分只涉及后端进程依赖，不改其决定。无过时提案或完全吸收的旧笔记。

## Alternatives considered

- 在 Go 复制四套键位表，修改局部且无需更新原生引擎，但会产生第二份输入算法，违反架构归属并可能与产品键位漂移。
- 让模型自行拼接按键码，无需增加接口，但无法核实零声母、微软分号键和方案差异，正是未核实答案产生的原因。
- 新增独立编码操作，语义更细；现有注音已经负责汉字到编码的转换，扩展显式方案即可复用读音与校验，并保留缺省行为。

## Testing

本分支以云端现有锁定提交 `7e7d3db308789e20f5de5fd693188fc6d2e6ed12` 为基线，只回移已合并的双拼反查修复（上游提交 `dfb1f5e765d841eccd1c4a51679db3a0ee8110c4`，PR #8265）。适配旧版 `profile` 的引用返回值，并仅测试该基线支持的四个方案，不升级候选排序、九键、日文或资源锁。直接升级最新 develop 会改变账号排序回放的既有契约，不能与本次反查一起上线。

四种方案的合成词反查、全部内置两键码往返、零声母、微软分号键、空音节与非法方案均保留回归覆盖。默认注音响应保持原样。回移版全部 1102 项 lib 单测通过，无失败或忽略；release 构建及生产同款模型、真实 MCP stdio 的四种方案调用通过。

锁定基线在 `session/candidates.rs` 给 `&str` 多借用一次，触发严格 clippy 和 wasm 门禁；移除该多余引用，与编译器原本的自动解引用等价，不改变候选逻辑。修正后全部 1102 项 lib 单测再次通过，严格 clippy 与格式检查通过。

## Consequences

新增响应仅在显式双拼请求出现，旧全拼调用保持兼容。词典没有词组读音时仍沿用逐字高频读法；编码成功不证明发布词库收录。遇到无法按当前方案解回原读音的音节，整次查询失败，避免提供部分按键码。云端必须随固定引擎提交一起部署才可使用新参数，不影响原生宿主的按键与会话路径。
